1. System Overview

CampaignOS is a multi-agent AI platform that takes a marketing brief (selected via a 7-step wizard) and produces a validated brief, creative strategy, and campaign copy — all grounded in real brand guidelines, customer data, and performance benchmarks from multiple GCP data sources.

What the System Does

📋
Brief Validation
Validates the campaign brief against real brand guidelines. Scores the Fan Truth (0-100), flags unrealistic KPIs, applies brand locks, cross-checks audience against CDP data.
💡
Creative Strategy
Generates the Big Idea, hero message, messaging pillars, channel priorities and budget allocation based on the validated brief and brand identity.
✍️
Campaign Copy
Writes short (OOH/KV), medium (social), and long (press) copy variants, plus CTA, Instagram caption, and TikTok hook — all brand-voice compliant.
👥
Audience Intelligence
Queries 2,216 real Kaggle customers + 1,597 Sephora products from pgvector to ground audience validation in real behavioural data.

2. The Briefing Agent — How It Was Built

The briefing agent is the first and most critical agent in the pipeline. It validates every incoming campaign brief against real data before any creative work begins. Here is exactly how it was constructed and why each decision was made.

Agent Architecture

The briefing agent uses the Google ADK 2.0 framework with a two-stage design:

POST /brief-full (FastAPI endpoint) │ ▼ ┌─────────────────────────────────────────────────────────┐ │ briefing_pipeline (ADK Workflow) │ │ │ │ Stage 1: load_brand_context [FUNCTION NODE — no LLM] │ │ ├── Load brand_guidelines.md from GCS │ │ ├── Query Vertex AI Search → brand rules summary │ │ ├── Query Vertex AI Search → fan truth examples │ │ ├── Query Vertex AI Search → channel benchmarks │ │ ├── Query pgvector CDP → audience insights │ │ └── Returns: BriefingContext (all data in one obj) │ │ │ │ Stage 2: briefing_agent [LLM — Groq Llama 3.3 70B] │ │ ├── Receives: BriefingContext + campaign brief │ │ ├── Scores Fan Truth (Specific/Shared/Special 0-100)│ │ ├── Validates KPIs vs benchmarks │ │ ├── Applies brand locks from guidelines │ │ ├── Cross-checks audience against CDP data │ │ └── Outputs: MachineBrief JSON │ └─────────────────────────────────────────────────────────┘ │ ▼ (if Groq/LiteLlm — direct fallback) ┌─────────────────────────────────────────────────────────┐ │ _run_briefing_with_groq() (runner.py) │ │ Constructs a single large prompt with ALL context │ │ Calls litellm.acompletion() → Groq API │ │ Parses JSON response → MachineBrief dict │ └─────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────┐ │ run_strategy_with_groq() → CreativeStrategy JSON │ │ run_copy_with_groq() → CampaignCopy JSON │ └─────────────────────────────────────────────────────────┘

Why Two Stages (Function Node + LLM)?

1

Data loading is deterministic — no LLM needed

Loading brand guidelines from GCS, querying Vertex AI Search, and fetching pgvector results are pure Python operations. Running them as a function node costs zero tokens and is 10× faster than asking an LLM to call tools.

2

All context pre-loaded → single LLM call

By the time the LLM runs, every piece of context (brand rules, fan truth benchmarks, channel benchmarks, audience CDP data) is already in memory. The LLM makes ONE call with complete information — no tool-calling loops needed.

3

ADK Workflow handles orchestration

The Google ADK Workflow DAG manages session state, data passing between nodes, and error handling. Each node's output becomes the next node's input automatically.

4

Groq direct fallback for LiteLLM compatibility

ADK's LiteLlm model integration has a known issue with Pydantic input_schema in Workflow DAGs. When the ADK agent returns no output, the runner detects this and calls Groq directly with the same context — ensuring reliable output regardless.

Agent Instructions (System Prompt Design)

The briefing agent's instructions follow the ADK 2.0 principle: instructions describe ROLE + BEHAVIOUR only. Data is injected via BriefingContext template variables — the LLM never needs to call tools to fetch data.

Key Design Principle

The prompt uses {BriefingContext.brand_guidelines}, {BriefingContext.fan_truth_summary} etc. as placeholders. These are filled by load_brand_context() before the LLM ever runs. This makes the LLM faster (no tool calls), cheaper (one API call), and more reliable (context is guaranteed to be present).

3. pgvector — Why, What, and How

pgvector is a PostgreSQL extension that adds a vector data type and similarity search operators. It enables "semantic search" — finding records by meaning rather than exact keyword match. This is the foundation of the CDP (Customer Data Platform) layer in CampaignOS.

Why pgvector Instead of a Dedicated Vector Database?

🐘
Familiar SQL Interface
pgvector uses standard PostgreSQL. All existing SQL tools, psycopg2 drivers, and BigQuery connectors work as-is. No new SDK to learn.
💰
Cost Effective
Dedicated vector DBs (Pinecone, Weaviate) cost $70-200/month. pgvector on Cloud SQL db-f1-micro costs ~$9/month. Same functionality.
🔗
Combines Structured + Vector
A single query can filter by brand, age range, AND rank by embedding similarity. Impossible to do this efficiently across separate databases.
☁️
GCP Native
Cloud SQL with pgvector integrates with Cloud Run via Unix socket (Cloud SQL Auth Proxy) — no VPC, no firewall rules, no public IP exposure needed.

What is an Embedding?

An embedding is a list of 384 numbers (a vector) that represents the meaning of a piece of text. Texts with similar meaning have embeddings that are close together in 384-dimensional space.

"Value-conscious student cook buys stock cubes for budget meals"
        ↓  SentenceTransformer('all-MiniLM-L6-v2')
[0.023, -0.187, 0.412, 0.091, ..., -0.334]   ← 384 numbers

"Budget-aware young cook uses flavour shortcuts"
        ↓
[0.031, -0.179, 0.398, 0.087, ..., -0.321]   ← similar numbers = similar meaning

Cosine similarity = 0.94 (very close!)  ← pgvector finds this instantly

How Semantic Search Works in CampaignOS

1

Seeding — generate embeddings for all records

When seeding the database, each row (customer, product, benchmark) is converted to a natural language description, then embedded into a 384-dim vector using SentenceTransformer('all-MiniLM-L6-v2'). The vector is stored in the embedding vector(384) column.

2

Query — embed the search query

When a campaign brief comes in with audience "Students 18-25, Instagram, TikTok", this text is also embedded into a 384-dim vector using the same model.

3

Search — cosine similarity with HNSW index

pgvector uses an HNSW (Hierarchical Navigable Small World) index to find the 3 most similar customer records in milliseconds. The <=> operator computes cosine distance.

4

Aggregate — extract meaningful insights

The top 3 matching customers are aggregated: average income, deal purchases per year, web visit frequency, channels inferred from behaviour. This real data is injected into the briefing agent's context.

-- How pgvector similarity search works:
SELECT brand, age_range, income, crm_notes, top_channels
FROM customer_insights
WHERE brand = 'Rnorr'
ORDER BY embedding <=> '[0.031, -0.179, 0.398, ...]'::vector   -- cosine distance
LIMIT 3;

-- Returns the 3 customers whose CRM notes are most similar
-- to the campaign brief's audience description

BigQuery is queried by the seed scripts to pull data into pgvector. The flow is: BigQuery (raw data) → Python script → embed with SentenceTransformer → pgvector (searchable). This separation means raw data is always queryable via SQL in BigQuery, while pgvector provides the fast semantic search layer.

Vertex AI Search (Discovery Engine)

Vertex AI Search indexes the brand guidelines text from GCS and provides AI-powered semantic search with summarisation. This is used in SEARCH_MODE=live.

🔍
Search App: campaignos-briefing-search
Datastore: campaignos-brand-guidelines → indexes brands/*/Guidelines/*.txt from GCS
Engine: Standard Edition — semantic search with snippet extraction
Queries run at runtime: brand rules, fan truth examples, channel benchmarks, moment type rules
Why .txt not .md? Vertex AI Search only accepts text/plain MIME type — markdown files must be renamed .txt before import

The BriefingSearchClient class in app/search_client.py makes 5 search queries per brief:

1. get_brand_rules(product_category, channels)
   → "brand guidelines: logo colour font voice guardrails for Dry Cook-In Sauces on Instagram..."

2. get_fan_truth_examples(product, product_category, audience)
   → "Fan Truth examples for Beef Stock Cubes targeting Students..."

3. get_campaign_benchmarks(product_category, market, season)
   → "Historical campaign performance for Dry Cook-In Sauces in UK during Summer..."

4. get_channel_benchmarks(channels, market, audience_segment)
   → "Channel benchmarks for Instagram, TikTok in UK targeting Students..."

5. get_moment_type_rules(moment_type)
   → "Day-to-Day campaign rules: budget weighting, approval requirements..."

Search results are injected into the BriefingContext and passed to the briefing agent as pre-loaded context. The agent never calls the Search API directly — all data arrives pre-loaded.

6. Docker — Local pgvector & Production Images

Docker for Local pgvector

Docker is used locally to run PostgreSQL with the pgvector extension — the same database engine that runs in Cloud SQL production. This means zero schema differences between dev and prod.

# docker-compose.pgvector.yml
services:
  pgvector:
    image: pgvector/pgvector:pg16      # PostgreSQL 16 with pgvector pre-installed
    container_name: campaignos-pgvector
    environment:
      POSTGRES_USER: campaignos
      POSTGRES_PASSWORD: campaignos
      POSTGRES_DB: marketing
      POSTGRES_HOST_AUTH_METHOD: trust  # No password needed from localhost
    ports:
      - "5433:5432"                     # 5433 on host → 5432 in container
                                        # 5433 avoids clash with local PostgreSQL on 5432
    volumes:
      - pgdata:/var/lib/postgresql/data # Persistent data across restarts

Why port 5433 and not 5432? The user's machine already had a native PostgreSQL installation running on port 5432. Mapping Docker to 5433 avoids the conflict. The production Cloud SQL always uses 5432 (the standard PostgreSQL port).

Docker for Production — Harness Image

The harness Docker image is designed to be small and fast to build. Key decisions:

DecisionReason
python:3.12-slim base imageMinimal OS — no dev tools, smaller attack surface
sentence-transformers excludedPyTorch alone is 1.5GB. Excluded from image since Cloud Run uses Vertex AI Search + pre-seeded pgvector embeddings at runtime
Only Guidelines/ folder copiedProduct images (300MB+) are loaded from GCS at runtime — no need in the image
uv for dependency managementuv installs Python deps 10× faster than pip and handles Python 3.12 download automatically
# Dockerfile (harness)
FROM python:3.12-slim
WORKDIR /app
RUN pip install uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev            # Install prod deps only
COPY main.py ./
COPY app/ ./app/
COPY bucket/brands/*/Guidelines/ ...     # Copy only text guidelines
ENV PORT=8080
CMD uv run uvicorn main:app --host 0.0.0.0 --port $PORT

Docker for Production — Frontend Image

# Dockerfile (frontend) — Multi-stage build
FROM node:20-alpine AS builder           # Stage 1: Build React app
WORKDIR /app
COPY package*.json ./
RUN npm ci                               # Clean install (faster than npm install)
COPY . .
ARG VITE_API_URL                         # Harness URL baked into the JS bundle at build time
RUN npm run build                        # Produces /app/dist/

FROM nginx:alpine                        # Stage 2: Serve with nginx (tiny ~20MB image)
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 8080
CMD ["nginx", "-g", "daemon off;"]

The multi-stage build means the final image only contains nginx + the static JS/CSS files. The Node.js toolchain (~500MB) is discarded after building. Final image size: ~30MB.

7. Cloud Build — Why and How

Why Cloud Build Instead of Local Docker Build?

⚡
Speed
Cloud Build runs in Google's data centre. Pushing a 400MB image to Container Registry (GCR) is a local network transfer for Cloud Build, versus uploading from your laptop over home broadband.
🏗️
No Docker Desktop Needed
Local Docker builds require Docker Desktop running. Cloud Build only requires the gcloud CLI — no local Docker daemon, no WSL, no memory overhead.
📦
Small Upload
With .gcloudignore excluding .venv (1GB) and brand assets (300MB+), only the source code (~1MB) is uploaded to Cloud Build. Much faster than uploading a full Docker context.
🔄
CI/CD Ready
Cloud Build can be triggered automatically from GitHub pushes, pull requests, or tags — enabling full automated deployment pipelines.

How Cloud Build Works

1

gcloud builds submit — uploads source to GCS

The gcloud CLI zips the local directory (respecting .gcloudignore) and uploads it to a Cloud Storage bucket. For our harness, this is ~1MB after exclusions.

2

Cloud Build fetches source and runs build steps

A Cloud Build worker (8 CPU high-performance machine) downloads the source, runs each step in cloudbuild.yaml sequentially: docker build → docker push → gcloud run deploy.

3

Docker image pushed to Container Registry (GCR)

The built image is pushed to gcr.io/PROJECT/campaignos-harness:latest. This is a local network transfer within GCP — much faster than uploading from a laptop.

4

gcloud run deploy creates a new Cloud Run revision

Cloud Run pulls the new image from GCR and creates a new revision. Traffic is shifted to the new revision automatically once health checks pass.

# cloudbuild.yaml (harness)
steps:
  # Step 1: Build Docker image
  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-t', 'gcr.io/$PROJECT_ID/campaignos-harness:latest', '.']

  # Step 2: Push to Container Registry
  - name: 'gcr.io/cloud-builders/docker'
    args: ['push', 'gcr.io/$PROJECT_ID/campaignos-harness:latest']

  # Step 3: Deploy to Cloud Run
  - name: 'gcr.io/google.com/cloudsdktool/cloud-sdk'
    args:
      - 'gcloud', 'run', 'deploy', 'campaignos-harness'
      - '--image=gcr.io/$PROJECT_ID/campaignos-harness:latest'
      - '--region=us-central1'
      - '--set-env-vars=PGVECTOR_HOST=/cloudsql/...,SEARCH_MODE=live,...'
      - '--set-secrets=GROQ_API_KEY=GROQ_API_KEY:latest'
      - '--add-cloudsql-instances=PROJECT:REGION:INSTANCE'

options:
  machineType: 'E2_HIGHCPU_8'   # 8 CPU build machine — faster than default

Cloud SQL Auth Proxy — How the Connection Works

The Cloud SQL Auth Proxy is the recommended way to connect Cloud Run to Cloud SQL. It creates a secure Unix socket file that your code connects to as if it were a local database.

Cloud Run Container │ ├── Your code (uvicorn + FastAPI) │ connects to: host=/cloudsql/PROJECT:REGION:INSTANCE │ user=campaignos, password=campaignos123 │ └── Cloud SQL Auth Proxy (auto-started by Cloud Run) │ Authenticates using the Container's service account │ Creates Unix socket at /cloudsql/PROJECT:REGION:INSTANCE/.s.PGSQL.5432 │ └── Cloud SQL (campaignos-pgvector) Receives connection as if from localhost No public IP exposure needed

This is configured with two Cloud Run settings:

# 1. Add Cloud SQL instance (creates the Unix socket)
--add-cloudsql-instances=dauntless-karma-497108-b0:us-central1:campaignos-pgvector

# 2. Tell pgvector_client.py to use the socket path
PGVECTOR_HOST=/cloudsql/dauntless-karma-497108-b0:us-central1:campaignos-pgvector
PGVECTOR_PORT=5432

10. Adding a New Brand

The system is designed so adding a new brand requires no code changes — only data and configuration.

1

Upload brand assets to GCS

Create folder gs://bucket/brands/{BrandName}/ with subfolders: Guidelines/, Logos/, Products/, Font/, Assets/, Colours/. The guidelines file MUST be named brand_guidelines.md.

2

Upload .txt version for Vertex AI Search

gsutil -h "Content-Type:text/plain" cp brand_guidelines.md gs://bucket/brands/{Brand}/Guidelines/brand_guidelines.txt — required because Vertex AI Search rejects .md files.

3

Re-index Search datastore

Run uv run python scripts/index_brand_assets.py to upload asset manifests and trigger a Vertex AI Search re-import to pick up the new brand guidelines.

4

Add brand to the React wizard (App.tsx)

Add to BRANDS array, BRAND_PRODUCTS, BRAND_CATEGORY, BRAND_FAN_TRUTHS, and INTERESTS — 5 constants, ~15 lines of code.

5

Seed CDP data for the new brand

Update map_to_brand() in seed_kaggle_cdp.py and seed_sephora_cdp.py with proxy signals for the new brand, then re-run both seed scripts.

6

Redeploy

gcloud builds submit --config cloudbuild.yaml for the frontend (new brand in wizard). No harness redeploy needed — harness reads brand data from GCS at runtime.

# Start harness

Production Deployment

# Deploy harness to Cloud Run
cd d:\campaignos\harness
gcloud builds submit --config cloudbuild.yaml --project=dauntless-karma-497108-b0

# Get harness URL then deploy frontend
$URL = gcloud run services describe campaignos-harness --region=us-central1 --format="value(status.url)"
cd d:\campaignos\frontend
gcloud builds submit --config cloudbuild.yaml --substitutions="_HARNESS_URL=$URL" --project=...

# Update a secret cleanly (no BOM)
$tmp = [System.IO.Path]::GetTempFileName()
[System.IO.File]::WriteAllText($tmp, "secret-value", [System.Text.Encoding]::ASCII)
gcloud secrets versions add SECRET_NAME --data-file=$tmp --project=...
Remove-Item $tmp
